# 订阅确认区域问题与简体中文名称布局设计

日期：2026-08-11

## 背景

订阅向导在最终提交失败时，目前只显示通用错误，管理员无法判断是哪个地区的官方商品确认、跳过状态或身份校验存在问题。与此同时，第三步把原商品名称与简体中文名称输入框放在同一行，长标题会挤压输入区域，不利于核对和编辑。

本次改动让可预判的地区问题以结构化数据从领域服务传到页面，并在一次提交中尽量列出全部相关地区；简体中文名称区域改为“原名称”和“输入框”上下两行展示，在桌面端提供稳定的编辑宽度，在窄屏上自适应。

## 目标

- 最终确认订阅失败时，明确显示每个有问题的地区中文名、地区代码和安全原因。
- 对同一次提交能够确定的多个地区问题进行聚合，而不是只报告最先失败的一项。
- 任何地区确认问题都不得产生游戏、名称目录、地区商品或订阅写入。
- 简体中文名称确认区分两行显示原名称与输入框，长标题可换行且不压缩输入框。
- 输入框在桌面端具有足够的可见宽度，在窄屏下不产生横向滚动，并继续遵守 120 字符上限。

## 非目标

- 不改变官方候选单选、跨区核验、手动链接或 AI 建议的业务时机。
- 不改变地区启用范围、订阅原子性、游戏身份、名称目录或价格来源规则。
- 不把第三方响应正文、数据库错误、堆栈、URL、凭据或其他内部信息返回浏览器。
- 不新增自动重试、部分地区保存、忽略失败地区或自动跳过地区的行为。

## 领域错误设计

### 结构化地区问题

领域层新增专用地区确认错误，并携带只读问题列表。每项只包含：

```ts
type SubscriptionRegionIssue = {
  regionCode: RegionCode;
  message: string;
};
```

`regionCode` 必须来自系统支持的 `US`、`JP`、`MX`、`BR`、`HK` 集合；领域层只返回预先定义的中文安全原因，不返回捕获到的原始异常文本。专用错误仍属于订阅确认错误体系，便于路由将其稳定映射为 422，但必须在通用校验错误之前处理。

### 预检聚合

在访问外部官方商品页面之前，服务先对整份提交执行集合级预检，聚合以下可确定问题：

- 已启用但既未确认也未跳过的地区；
- 同时出现在确认列表和跳过列表的地区；
- 重复提交的地区；
- 不属于当前启用范围的确认或跳过地区。

完全不属于受支持集合的非法地区值无法安全映射为 `SubscriptionRegionIssue`，继续按普通输入校验错误返回 422，不伪造地区项。同一合法地区在一次响应中最多出现一次。若一个地区同时违反多条规则，使用最具体且最有助于管理员操作的安全原因；服务不拼接底层异常。预检存在问题时立即抛出结构化地区错误，不发起官方站点请求，也不执行任何持久化。

### 各地区官方复核聚合

预检通过后，服务并行复核本次提交的各地区官方商品。实现使用可收集全部结果的等待方式，确保多个地区同时发生可预期业务失败时都能报告，例如：

- 官方商品无法重新确认；
- 商品身份与当前游戏不一致；
- 自动匹配依据已失效；
- 日本区升级包与本体关系不符合规则；
- 地区确认来源或手动链接状态无效。

上述已知业务错误被转换为对应地区的问题项。若任一复核出现未知程序、网络基础设施或数据层异常，整体按内部错误处理并返回脱敏 500，不返回部分地区问题，避免把不完整结果误导为全部原因。

只有全部预检、地区复核、名称校验和既有业务校验通过后，服务才进入原有原子写入流程。任何错误路径均保持零写入。

### 顺序与去重

问题列表按固定地区顺序输出：美国 `US`、日本 `JP`、墨西哥 `MX`、巴西 `BR`、香港 `HK`。不依赖请求数组顺序或并发完成顺序。页面也沿用同一顺序，以便测试稳定且管理员容易扫描。

## HTTP 合同

地区确认失败使用 422：

```json
{
  "code": "REGION_CONFIRMATION_FAILED",
  "error": "以下地区无法确认，请处理后重试。",
  "regionIssues": [
    {
      "regionCode": "JP",
      "message": "官方商品确认失败，请重新核验。"
    },
    {
      "regionCode": "HK",
      "message": "尚未确认或跳过该地区。"
    }
  ]
}
```

既有非地区输入错误继续返回 `VALIDATION_ERROR`；未知异常继续返回固定 500。两者均不得附带 `regionIssues`。401 认证合同保持不变。

路由必须严格序列化领域错误中的允许字段，不直接展开错误对象。服务端对地区代码、问题数量和消息类型负责；客户端仍将响应视为不可信输入，只接受支持的地区代码和合法的非空消息，畸形问题项忽略并回退到通用错误提示。

## 客户端与页面状态

`ProductApiError` 增加可选的只读 `regionIssues`。解析器只在响应是对象、`regionIssues` 是数组、条目字段类型正确且地区代码受支持时保留条目；不得把响应中的额外字段带入应用状态。

订阅向导增加独立的 `confirmationRegionIssues` 状态，不把结构化列表塞入单一通知字符串。提交失败且收到合法地区问题时：

- 显示统一摘要“以下地区无法确认，请处理后重试。”；
- 在确认区显示可访问的错误列表；
- 每行格式为“地区中文名（代码）：原因”，例如“日本（JP）：官方商品确认失败，请重新核验。”；
- 多个地区全部显示，不折叠为“部分地区失败”；
- 页面不得显示原始英文异常、URL 或响应正文。

错误列表使用适合屏幕阅读器的警报语义，但避免摘要和列表同时重复播报。提交新一轮确认前先清空旧问题；搜索新商品、切换或取消官方候选、重新核验地区、修改或解析手动链接、选择地区候选、切换跳过状态时也清空旧问题，防止已失效的地区结论残留。只编辑简体中文名称时无需清空地区问题，因为该操作不改变地区状态。

## 简体中文名称布局

第三步使用专用布局，不再复用把标题和控件横向挤在一起的通用地区选项样式：

1. 第一行显示固定标签“原名称”和当前官方候选的 `canonicalTitle`。标题允许自然换行，不截断，不写入输入框占位符。
2. 第二行显示固定标签“简体中文名称”和文本输入框。标签与输入框建立显式关联，输入框继续为必填。
3. AI 建议、目录建议或手工输入的来源说明放在输入框下方，不与原名称混排。

桌面端输入区域占满可用空间，并在容器允许时具有至少约 640px 的可见宽度；输入框高度不低于 46px。窄屏断点下标签和输入区纵向排列，输入框宽度为 `100%`、`min-width: 0`，不得造成页面横向滚动。输入框显式设置 `maxLength={120}`，与服务端名称长度上限一致；CSS 不以固定宽度破坏响应式布局。

## 测试策略

### 服务测试

- 一次提交缺少多个已启用地区时，返回所有对应地区并按固定顺序排列。
- 多个地区的官方复核分别产生已知业务失败时，聚合所有问题。
- 重复、重叠、范围外的合法地区正确去重并给出安全原因；非法地区值保持普通 422。
- 未知异常仍按内部错误处理，不降级成地区问题。
- 所有地区问题路径断言零写入；成功路径维持原有写入和请求数量。

### 路由与客户端测试

- 专用领域错误映射为 `REGION_CONFIRMATION_FAILED`、422 和严格 `regionIssues` 形状。
- 通用 422、401 和 500 合同保持不变且不携带地区列表。
- 客户端解析合法列表，忽略不受支持的地区、错误字段类型和额外字段。

### DOM 与样式合同测试

- 一个或多个问题以“中文地区名（代码）：原因”完整显示并保持固定顺序。
- 新提交和各项相关状态变更会清空旧地区问题。
- 原名称与输入框分别位于两行；长标题可换行。
- 输入框具有可访问标签、`required`、`maxLength=120` 和专用样式类。
- 样式合同覆盖桌面约 640px 的最小可见宽度、至少 46px 高度以及窄屏 `width: 100%`、`min-width: 0`。
- 现有单选候选、成功确认、AI 建议时机与人工编辑回归继续通过。

## 验收标准

- 管理员能从一次失败结果中看清所有已检测到的问题地区、代码和操作性原因。
- 不会因并发完成顺序而丢失、重复或打乱地区问题。
- 结构化错误和未知错误均不泄漏内部信息，失败时数据库无部分写入。
- 长英文、日文或繁体原标题不会挤压简体中文名称输入框。
- 桌面端输入框便于编辑，手机或窄窗口下无横向滚动，前后端均执行 120 字符上限。
