# PostgreSQL 登录失败状态并发竞态修复设计规格

状态：方案已确认，待测试先行实施

日期：2026-07-30

## 1. 背景与问题证据

Task 10 提交前的完整质量门禁共运行 435 个测试，其中 434 个通过；失败用例为“六个同快照并发登录只允许前五个进入密码验证并拒绝第六个正确密码”。该用例单独重复运行时约在第 7 次出现同类失败，说明这不是稳定的业务断言错误，而是由事务调度顺序触发的真实并发竞态。

当前 PostgreSQL 认证仓储在同一事务中按以下顺序取得登录失败状态：

1. 以 `FOR SHARE` 锁定 `admin_credentials(id = 1)`；
2. 执行 `INSERT ... ON CONFLICT DO NOTHING`，尝试创建 `login_attempts(id = 1)`；
3. 再执行独立的 `SELECT ... FOR UPDATE`，读取并锁定该状态行。

当数据库已有一条已提交的失败状态时，合法登录会锁住并准备删除该行；并发事务的 `INSERT ... DO NOTHING` 因当时已存在唯一键而不负责创建替代行，后续独立 `SELECT ... FOR UPDATE` 则等待合法登录持有的行锁。合法登录删除并提交后，该 `SELECT` 可返回零行，最终抛出内部错误“登录资格锁定未返回状态”。该结果违反认证服务的外部契约：错误密码应得到无凭据泄漏的认证失败，而不是内部错误。

额外的真实 PostgreSQL 诊断证明：若合法登录在自己的事务内首次创建并删除此前不存在的状态行，等待事务可以重新插入替代行，旧实现的用例单次及连续二十次都不会形成预期 RED。因此，确定性回归必须从已提交的 `login_attempts` 行开始；这项修正只收紧测试时序，不改变原子 upsert 的生产修复方向。

## 2. 必须保持的认证约束

本次修复只消除 PostgreSQL 实现中的“确保行存在”和“锁定并读取行”之间的空档，以下约束全部保持不变：

- 系统仍只有 `id = 1` 的单一管理员凭据和单一登录失败状态。
- 登录与密码恢复继续遵循 `admin_credentials -> login_attempts` 的统一加锁顺序，避免形成反序死锁。
- 活跃锁定必须在 PBKDF2 密码校验前返回，已被锁定的请求不得消耗密码验证资源。
- 同一失败窗口内，前五次错误密码必须逐次串行累计；达到阈值后，第六个请求即使密码正确也必须被锁定状态拒绝。
- 合法登录清理失败状态、写入会话摘要和事务提交仍是一个原子操作；会话插入失败时不得遗失原失败计数。
- 密码恢复仍负责清理失败状态和撤销活动会话，接口、Cookie、恢复码及会话安全规则不变。
- 日志、异常和测试协调器均不得记录密码、密码哈希、盐、原始会话令牌或真实恢复码。

## 3. 已确认方案

把原来的 `INSERT ... DO NOTHING` 与独立 `SELECT ... FOR UPDATE` 合并为一条原子语句：

```sql
INSERT INTO login_attempts (id, failed_count, locked_until)
VALUES (1, 0, NULL)
ON CONFLICT (id) DO UPDATE
SET failed_count = login_attempts.failed_count,
    locked_until = login_attempts.locked_until
RETURNING failed_count AS "failedCount",
          locked_until AS "lockedUntil"
```

该语句同时承担三项职责：

1. 状态不存在时创建默认行；
2. 状态已存在时通过冲突更新路径取得该行的排他锁，同时原样保留失败次数与锁定截止时间；
3. 无论走插入还是冲突更新路径，都由 `RETURNING` 在同一语句中返回本事务实际锁定的状态。

PostgreSQL 会在冲突行由另一事务占用时等待并重新完成冲突处理。如果前一合法登录在提交前删除了状态行，等待中的语句会在可见性变化后完成插入或冲突更新；它不会像原来的两条语句那样，在冲突处理与读取之间暴露“行已消失”的时间窗口。

`login_attempts` 没有更新时间触发器，本次自赋值更新不会改变业务字段。该表固定为单例，登录本来就需要在此串行化失败计数，因此不会引入新的业务级写放大或并发范围。

## 4. 事务与错误处理

原有事务边界保持不变：

1. 读取并共享锁定管理员凭据；
2. 用原子 upsert 锁定并取得失败状态；
3. 若锁定仍有效，直接返回锁定结果；
4. 否则校验密码，并串行更新失败计数，或在成功时删除失败状态并写入会话摘要；
5. 一并提交或回滚。

正常情况下，原子 upsert 必须返回一行。仓储仍保留“零行即内部不变量破坏”的保护，但只抛出不包含 SQL、参数或凭据的通用内部错误；业务层不得把数据库细节暴露给客户端。

本次不改为永久保留失败状态行。合法登录和密码恢复后继续删除该行，保留既有“无失败状态即无记录”的数据语义。

## 5. 测试先行方案

实现前先增加一个真实 PostgreSQL 回归测试。测试通过仅用于测试的数据库/事务包装器协调执行时序，不模拟 SQL 结果，也不替换 PostgreSQL 的真实锁和事务行为：

1. 初始化管理员凭据，并先完成一次错误登录，建立 `failed_count = 1` 的已提交 `login_attempts` 行；
2. 启动合法登录事务，使其锁定既有失败状态；在它即将执行真实的 `DELETE FROM login_attempts` 前暂停；
3. 启动另一个错误密码登录。旧实现由测试包装器先把独立 `SELECT ... FOR UPDATE` 提交给真实 PostgreSQL，新实现则先把原子 upsert 提交给真实 PostgreSQL；包装器随后发出到达信号，保证协调不依赖延时猜测；
4. 释放合法登录事务，让它执行真实删除并提交；随后等待错误密码登录的锁定语句继续；
5. 断言等待中的登录最终得到标准的无效凭据结果，而不是“登录资格锁定未返回状态”或其他内部错误；
6. 断言错误密码被计为新的失败窗口第一次，成功会话仍只保存摘要，且协调器不采集秘密参数。

该回归测试在旧的两语句实现下应稳定失败，在原子 upsert 实现下稳定通过。现有以下用例继续作为兼容性保护：

- 五个并发错误登录完成后的五次阈值，以及后续正确密码在密码校验前被锁定；
- 活跃锁定在密码验证前短路；
- 锁定到期后重新累计；
- 合法登录清理失败状态并原子创建会话；
- 密码恢复与并发登录的会话撤销顺序；
- PostgreSQL 迁移约束和 D1 认证行为。

## 7. 未采用方案

### 永久保留单例失败状态行

合法登录和密码恢复时把计数重置为零而不是删除行，也能减少“行消失”的情况，但会改变现有数据语义，并需要系统性检查初始化、恢复和测试清理路径。本次问题可在不扩大范围的情况下解决，因此不采用。

### PostgreSQL 事务级 advisory lock

在读写失败状态前取得固定 advisory lock 也能串行化登录，但它引入一套与表行锁并行的锁协议，增加密码恢复、测试和后续维护的认知成本。单条 upsert 已能利用现有唯一键和行锁解决竞态，因此不采用。

并发请求之间不定义客户端数组顺序或密码摘要完成顺序。阈值测试必须先等待五个错误请求全部完成并确认锁定已经形成，再提交正确密码验证锁定短路；不得把“同时创建的第六个 Promise”当作 PostgreSQL 必须最后授予行锁的业务保证。
