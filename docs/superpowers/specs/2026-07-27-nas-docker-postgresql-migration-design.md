## 1. 背景与目标

当前生产系统使用 Cloudflare Workers Static Assets、D1、Cron Trigger、Secrets 与 Browser Binding。源码已经按前端、路由、服务、仓储和提供方拆分，但生产部署产物会被打包为单个 Worker bundle；同时，运行时、数据库、定时任务和日区升级包浏览器能力均依赖 Cloudflare。

本次迁移的目标不是继续维护双平台兼容，而是以群晖 NAS 上的 Docker Compose 作为唯一生产环境，并在完成等价验收后停止使用 Cloudflare。迁移必须保持现有单管理员认证、订阅管理、五区商品发现和价格采集、历史、设置、导出、Telegram 日报与即时通知、日区升级包浏览器关系发现等全部业务能力。

开发和发布必须在本地 M1 完成验证，再由 GitHub Actions 构建并推送公开的多架构 Docker Hub 镜像。NAS 只拉取固定版本镜像并启动 Compose，不在设备上下载源码、安装 Node 依赖或构建应用。

## 2. 已确认范围

### 2.1 范围内

- 完全移除 Cloudflare Worker、D1、Cron Trigger、Static Assets Binding、Secrets 与 Browser Binding 的生产依赖。
- 使用一个 Node.js 应用容器提供同源 API、React 静态资源、SPA 回退、定时任务和本地 Playwright。
- 使用项目专属 PostgreSQL 容器、独立数据库、独立最小权限用户和持久化目录。
- 使用本地 Chromium 保留日区升级包自动发现与保存前关系复核。
- 保留当前全部业务功能、业务安全规则、价格来源约束和管理员操作边界。
- 支持 M1 本地开发、容器化生产验收、PostgreSQL 集成测试和 Chromium 冒烟测试。
- 通过 GitHub Actions 发布 `linux/arm64` 与 `linux/amd64` 的公开 Docker Hub 多架构镜像。
- 提供群晖 Docker Compose、环境变量示例、备份恢复、升级回滚和排障文档。

### 2.2 范围外

- 不迁移现有 D1 数据；NAS 使用全新空数据库并重新初始化管理员。
- 首阶段只验收局域网访问，不设计 FRP、公网域名、TLS 终止、WAF 或公网限流。
- 不提供 Cloudflare 与 NAS 双平台运行模式，也不保留模拟 D1 或 Binding 的长期兼容层。
- 不引入多用户、横向扩容、分布式任务队列、独立浏览器服务或 Kubernetes。
- 不在 Docker 镜像、Compose 文件或 GitHub 仓库中保存真实数据库密码、Telegram 凭据、管理员密码、恢复码或会话令牌。

## 3. 方案选择

### 3.1 采用方案

采用两个常驻容器：

```text
局域网浏览器
     │ HTTP
     ▼
app 容器
  ├─ Node.js HTTP 服务
  ├─ React 静态页面与 SPA 回退
  ├─ 现有 API 路由与业务服务
  ├─ 每分钟和每六小时调度器
  └─ 本地 Playwright + Chromium
     │ 仅 Compose 内部网络
     ▼
postgres 容器
  └─ 项目专属数据库与用户
```

`app` 是唯一对 NAS 映射端口的服务。PostgreSQL 不映射宿主机端口，Chromium 不开放调试或远程控制端口。常驻环境不增加任务队列、浏览器服务或备份守护容器。

### 3.2 未采用方案

- **拆分 Web、调度器与浏览器容器**：隔离更强，但需要跨容器任务协议、队列和额外故障恢复，对单管理员 NAS 项目复杂度过高。
- **Cloudflare API 兼容层**：初期改动较少，但会把 `D1Database`、`Fetcher`、`scheduled()` 等平台概念长期留在新架构中，不符合彻底迁出的目标。
- **SQLite**：最接近 D1 SQL 方言，但用户已确认使用项目专属 PostgreSQL；PostgreSQL 也便于统一 NAS 上的数据库备份和运行维护。

## 4. 代码与组件边界

目标代码结构保持现有业务分层，并收敛平台装配：

```text
src/
  app/                         React 前端
  server/                      Node HTTP、静态资源、生命周期与依赖装配
  shared/                      前后端共享领域模型
  routes/                      同源 API 路由
  services/                    业务服务和调度规则
  providers/                   任天堂、汇率、Telegram 等外部来源
    playwright/                本地 Chromium 适配器
  repositories/
    postgres/                  PostgreSQL 仓储实现
migrations/
  postgres/                    按版本排序的 PostgreSQL SQL 迁移
scripts/
  backup-postgres.*            受控备份入口
  restore-postgres.*           受控恢复入口
```

现有使用标准 `Request`、`Response`、`fetch`、Web Crypto 和 `AbortSignal` 的业务代码应尽量复用。Cloudflare 平台类型只能在迁移过渡期间存在；最终验收要求生产源码和依赖不再引用 Wrangler、D1、Worker Handler 或 Browser Binding。

Node 入口负责依赖装配，不吸收业务判断。路由继续负责认证守卫、请求解析和安全错误映射；服务继续负责业务规则；仓储负责 SQL、事务和行模型转换；提供方负责外部来源校验与脱敏失败分类。

## 5. HTTP、前端与认证

### 5.1 请求处理

应用使用 Node.js 22 和轻量标准 Fetch API 适配层。请求顺序固定为：

1. `/api/health` 无凭据健康检查。
2. 认证、设置、仪表盘、刷新、历史、导出、商品和订阅 API。
3. 构建后的 React 静态资源。
4. 非 API 前端路径回退到 `index.html`。

未知 `/api/*` 路径必须返回 API `404`，不得回退前端。前端与 API 保持同源，不启用 CORS。请求体设置显式大小上限，外部输入继续在路由和服务边界做类型、枚举、URL、地区和商品身份验证。

### 5.2 局域网认证

现有单管理员安全规则全部保留：

- 仅空数据库首次开放初始化。
- 密码与恢复码只保存加盐派生哈希。
- 恢复码仅显示一次，成功重置后永久失效。
- 会话 Cookie 中的原始令牌不写入数据库，只保存 SHA-256 摘要。
- 连续五次失败锁定十五分钟；成功登录或锁定结束后清理失败状态。
- 单设备退出只撤销当前会话；密码重置撤销全部会话。

Cookie 固定使用 `HttpOnly` 与 `SameSite=Strict`。局域网 HTTP 首阶段通过 `COOKIE_SECURE=false` 明确关闭 `Secure`；未来接入 HTTPS 时必须改为 `true`，认证代码无需再次修改。应用不得根据请求头自动降低 Cookie 安全级别。

## 6. PostgreSQL 数据设计

### 6.1 技术选择

使用 `pg` 连接池与显式参数化 SQL，不引入 ORM。原因是当前仓储已经使用清晰的 SQL 和行模型转换，直接迁移能减少业务层改动并保留查询可审计性。

默认连接池上限为 5，满足单管理员和定时任务场景。官方镜像的 `POSTGRES_USER` 仅用于首次空目录引导并保留在 postgres 容器；只读 init hook 用该 bootstrap 管理角色在单事务中创建独立普通项目所有者，明确关闭超级、建角、建库、复制和绕过 RLS 能力。应用从第一次连接起只取得普通角色 `DATABASE_URL`，不取得 bootstrap 用户名或密码。

### 6.2 类型与约束

- SQLite `INTEGER` 布尔值迁移为 PostgreSQL `BOOLEAN`。
- ISO 时间文本迁移为 `TIMESTAMPTZ`，应用与数据库统一使用 UTC。
- 设置中的结构化数组和对象迁移为 `JSONB`，服务层继续执行地区白名单和业务关系验证。
- 自增日志与快照主键迁移为 `BIGINT GENERATED BY DEFAULT AS IDENTITY`。
- 金额继续使用整数最小货币单位，禁止用浮点数保存价格。
- 现有外键、唯一约束、目标状态约束、单管理员单行约束和删除规则必须等价保留。
- 查询继续使用参数占位符，任何用户值、排序值或筛选值不得直接拼接 SQL。

### 6.3 事务

所有原 D1 `batch()` 业务原子边界改为显式事务：

- 批量订阅确认任一地区失败时零写入。
- 地区补全只原子追加缺失地区。
- 永久删除先验证全部目标，再在同一事务按依赖顺序清理。
- 密码重置、恢复码失效和全会话撤销保持原子。
- 通知事件只有在 Telegram 明确成功后才更新为已投递。

事务回调不得把数据库客户端泄漏到业务层。异常路径必须回滚，返回给浏览器的错误只使用预定义安全分类。

### 6.4 迁移

迁移文件按不可变版本编号执行，并由专用迁移表记录。应用启动时先等待 PostgreSQL 健康，再取得数据库 advisory lock，按顺序执行未应用迁移；多个意外应用实例不得并发迁移。

迁移校验和发生变化时必须停止启动，不能静默重跑被修改的历史迁移。破坏性迁移必须拆成“先兼容写入、再独立清理”的后续版本，使上一应用版本至少在一个发布窗口内仍可回退。

本次使用全新数据库，因此不实现 D1 导出导入工具。

## 7. 定时任务

应用进程内保留两个调度边界：

- 每分钟：按管理员 IANA 时区判断日报时刻，并重试待发送即时通知。
- 每六小时：执行价格采集、每日汇率读取、价格历史保留和九十天采集日志清理。

触发时刻以 UTC 为基础，业务层继续处理管理员时区。每项任务执行前取得专用 PostgreSQL advisory lock；未取得锁时安全跳过本轮，防止任务重叠、容器短暂重复启动或人工误启第二实例造成重复采集和通知。

任务异常只记录脱敏摘要，不终止 HTTP 服务。容器收到终止信号时停止创建新任务、停止接受新 HTTP 请求，并在限定宽限期内等待正在执行的事务和浏览器清理完成；超过上限后安全退出，由现有幂等和通知状态规则处理下一轮恢复。

## 8. 本地 Playwright

Cloudflare Browser Binding 改为镜像内固定版本的 Playwright 与 Chromium。Playwright 包版本和浏览器安装版本必须一致，并进入依赖锁文件与镜像构建缓存键。

现有日区升级包规则保持不变：

- 只允许已验证的任天堂日区根商品 URL，禁止任意 URL 导航。
- 每个关系请求最多启动一个浏览器。
- 每批最多三个商品，按输入顺序串行处理。
- 每项创建全新隔离上下文，单项最多三十秒，不自动重试。
- 自动候选保存前重新验证根商品、唯一关系 URL 和 JP/JPY/在售/同 ID 价格。
- 页面、上下文和浏览器在成功、超时、取消、关闭拒绝及未预期异常路径都执行受控清理。
- Chromium 不接收 PostgreSQL、Telegram 或管理员认证凭据，不开放调试端口，不参与六小时采集或日报。

应用容器以非 root 用户运行，启用 init 进程避免僵尸子进程，为 Chromium 提供独立临时目录与足够共享内存，并限制 Linux capabilities。Compose 配置须在 M1 与 DS423+ 上分别完成真实浏览器启动验收；不得为解决启动失败而开放任意主机网络、特权容器或未受控调试接口。

## 9. Docker 与群晖部署

### 9.1 镜像

Dockerfile 使用多阶段构建：

1. 固定 Node.js 与 npm 依赖，执行可重复安装。
2. 构建 React 静态资源和 Node 服务端产物。
3. 生成只包含生产依赖、编译产物和固定 Chromium 的运行镜像。
4. 以非 root 用户启动应用，不复制源码控制文件、测试夹具、`.env` 或真实数据。

镜像同时发布 `linux/arm64` 和 `linux/amd64` manifest。M1 本地原生运行 arm64，DS423+ 自动拉取 amd64。

### 9.2 Compose

生产 Compose 只引用公开镜像，不包含 `build:`。两个常驻服务均配置健康检查和重启策略：

- `app` 等待 PostgreSQL 健康与迁移成功后启动 HTTP 和调度器。
- `postgres` 使用固定主版本镜像、项目专属数据库与内部网络。

推荐群晖目录：

```text
/volume1/docker/switch-price-monitor/
  ├─ docker-compose.yml
  ├─ .env
  ├─ docker/postgres/init-app-role.sh
  ├─ postgres-data/
  └─ backups/
```

实际根目录由 `.env` 显式指定，不在仓库中硬编码用户卷名。`postgres-data` 首次启动必须为空；官方入口对非空目录不会再次执行 init hook，普通角色健康检查必须保持失败并阻止 app 启动。init hook 是只读部署资产，由 `.dockerignore` 排除且不进入 app 镜像。PostgreSQL 数据和备份使用可由群晖备份工具识别的独立目录。只有应用 HTTP 端口映射到 NAS。

### 9.3 配置

仓库提供不含真实值的 `.env.example`。运行配置至少包含：

- Docker Hub 镜像名与固定版本。
- 应用监听端口和 NAS 映射端口。
- PostgreSQL 数据库名、bootstrap 管理用户/随机密码、普通应用用户/独立随机密码，以及只使用普通角色的 URL 编码 `DATABASE_URL`。
- `COOKIE_SECURE` 与日志级别。
- 可选 Telegram Bot Token 与 Chat ID。
- 数据、备份目录及备份保留份数。

管理员密码仍由首次初始化页面设置。任何秘密不得作为 Docker build argument、镜像层、GitHub Actions 普通日志或 Compose 示例值。

## 10. 本地开发

M1 本地提供两种可重复模式。

### 10.1 开发模式

- 前端启用热更新。
- Node API 支持调试和增量重启。
- 使用专属开发 PostgreSQL 容器，不连接 NAS 或生产数据。
- 本地 Playwright 使用与生产锁定的版本和 Chromium。
- 开发环境可使用独立端口与测试 Telegram 空配置，禁止复用真实生产凭据。

### 10.2 生产验收模式

- 使用与发布相同的 Dockerfile 构建 `linux/arm64` 镜像。
- 使用生产形态 Compose、静态前端、自动迁移、健康检查和非 root 用户。
- 从空数据库覆盖首次初始化、核心业务与浏览器启动。
- 验收通过后才允许创建发布标签。

本地开发脚本和 Compose 覆盖文件不得改变生产业务语义，只能调整挂载、端口、热更新和日志详细度。

## 11. GitHub Actions 与 Docker Hub

Docker Hub 使用公开仓库。GitHub 仓库只保存以下发布凭据：

- `DOCKERHUB_USERNAME`
- 仅具备目标仓库写入权限的 `DOCKERHUB_TOKEN`

### 11.1 普通提交与 Pull Request

工作流必须执行：

- 锁定依赖安装。
- 纯业务单元测试。
- 真实 PostgreSQL 服务容器集成测试。
- React/jsdom 测试。
- Chromium 生命周期测试与本地浏览器冒烟测试。
- TypeScript 严格检查。
- 生产前后端构建。
- Docker 镜像构建验证，但不登录或推送 Docker Hub。
- 差异空白、敏感信息和中文注释一致性检查。

### 11.2 版本标签发布

只有 `v*` 语义化版本标签触发正式发布。工作流先重复完整质量门禁，再使用 Buildx 发布：

```text
${DOCKERHUB_IMAGE}:0.1.0
${DOCKERHUB_IMAGE}:0.1
${DOCKERHUB_IMAGE}:sha-${GIT_SHA_SHORT}
${DOCKERHUB_IMAGE}:latest
```

`DOCKERHUB_IMAGE` 是工作流根据已配置 Docker Hub 用户名形成的完整公开仓库名，`GIT_SHA_SHORT` 是触发标签所指提交的固定短哈希。`latest` 只指向通过全部门禁的正式稳定标签，不由普通分支推送更新。镜像元数据记录源仓库、Git commit、语义版本和构建时间。依赖、基础镜像和 GitHub Actions 使用固定版本；发布日志不得打印 Docker Hub Token 或运行时秘密。

## 12. 备份、恢复、升级与回滚

### 12.1 备份

提供调用固定 PostgreSQL 客户端版本的 `pg_dump` 脚本：

- 使用压缩自定义格式。
- 先写同目录临时文件，成功后原子改名。
- 文件名包含 UTC 时间与数据库标识。
- 默认保留最近十四份，可通过环境变量调整。
- 失败时保留上一份成功备份并返回非零退出码。
- 可由群晖任务计划每日调用，不新增常驻备份容器。

### 12.2 恢复

恢复必须：

1. 停止 `app`，防止恢复期间写入。
2. 创建全新空数据库或空数据目录。
3. 使用匹配主版本的 `pg_restore` 恢复。
4. 校验迁移版本、核心表计数、外键与管理员状态。
5. 启动固定应用版本并通过健康、登录和只读查询验收。

恢复脚本不得默认覆盖正在运行的数据库；目标不为空时必须明确失败。

### 12.3 升级与回滚

NAS 通过修改 `APP_VERSION`、拉取镜像并重建 `app` 容器升级。生产 Compose 锁定精确版本，不直接依赖 `latest`。

每次升级保留上一镜像标签。应用错误可回退上一镜像；数据库迁移必须保证上一版本在一个发布窗口内可读。若迁移已经包含不可逆清理，则只能按已验证备份恢复流程回滚，发布说明必须明确这一边界。

## 13. 错误处理与可观测性

- `app` 与 `postgres` 均提供健康检查；应用健康检查区分进程存活与数据库就绪。
- PostgreSQL 暂时不可用时按有上限退避等待；迁移校验失败时明确停止，不进入错误结构下的业务运行。
- 外部任天堂、汇率和 Telegram 请求继续使用超时、有限重试和受控失败分类。
- 日志写入标准输出供群晖 Container Manager 查看，使用结构化时间、模块、事件和安全摘要。
- 日志禁止出现密码、恢复码、原始会话令牌、数据库密码、Telegram 凭据、浏览器会话标识、页面正文或完整第三方响应。
- 浏览器、定时任务或单一外部来源失败不得导致 HTTP 服务无条件退出；数据库结构错误和必要配置错误必须阻止启动。

## 14. 测试策略

迁移继续遵循测试先行：每个行为变更先增加失败测试，再实现最小代码。所有新增或修改的源代码、测试、SQL、Docker、GitHub Actions 与运行配置必须包含中文详细注释，解释职责、数据约束、边界条件和安全或业务原因。

### 14.1 保留与替换

- 纯领域、业务服务、价格规则、来源解析和 React 测试尽量原样保留。
- Cloudflare 测试池和 D1 集成测试替换为 Node + 真实 PostgreSQL 服务容器。
- Worker Handler 测试替换为 Node HTTP Fetch 适配测试。
- Browser Binding 测试保留可注入浏览器接口，生产适配改为本地 Playwright。

### 14.2 必须新增

- PostgreSQL 类型映射、外键、唯一约束与迁移顺序测试。
- 批量确认、补全、删除、密码重置和通知回写的事务回滚测试。
- advisory lock 下的迁移与调度互斥测试。
- 静态资源、SPA 回退、API `404`、请求大小和 Cookie 配置测试。
- SIGTERM 优雅关闭和任务宽限期测试。
- arm64 本地与 amd64 发布镜像的 Chromium 启动契约测试。
- Compose 健康依赖、非 root 用户、内部数据库端口和秘密缺失失败测试。
- 备份生成、空库恢复、版本校验和非空目标拒绝测试。
- GitHub Actions 标签到 Docker Hub 标签的映射测试。

真实任天堂页面只进入受控本地或 NAS 冒烟验收，不进入每次普通单元测试；普通测试使用固定夹具和可注入替身，避免外部页面波动造成错误发布阻塞。

## 15. 交付与验收

迁移完成必须同时满足：

1. M1 开发模式可运行前端、API、PostgreSQL 与 Chromium。
2. M1 生产验收 Compose 可从空数据库启动。
3. 首次初始化、登录、退出、恢复码、失败锁定和会话撤销正常。
4. 五区商品发现、订阅确认、补全、详情、删除、历史和 CSV 导出正常。
5. 手动刷新、六小时采集、每分钟日报判断和数据保留正常。
6. Telegram 日报、降价、采集异常和恢复通知正常。
7. 日区升级包由本地 Chromium 完成候选发现与保存前二次关系复核。
8. PostgreSQL 事务失败时没有部分订阅、部分删除或错误通知状态。
9. 备份可恢复到全新 PostgreSQL 数据库并通过登录与核心读取校验。
10. GitHub Actions 在发布标签上生成同时包含 arm64 与 amd64 的公开 Docker Hub 镜像。
11. DS423+ 只凭 Compose、`.env`、只读 PostgreSQL init hook 和固定镜像标签即可从空数据目录启动，不需要应用源码和构建工具。
12. NAS 上 PostgreSQL 和 Chromium 没有对局域网暴露端口。
13. 全部测试、类型检查、生产构建、容器检查、敏感信息扫描和注释一致性检查通过。
14. 生产源码、依赖与部署配置不再引用 Wrangler、D1、Worker Handler、Cloudflare Cron 或 Browser Binding。
15. NAS 完成功能等价验收后，才停止并删除 Cloudflare 生产资源；删除前保留最终配置与非敏感验收记录。

## 16. 实施约束

- 实施必须按独立计划拆分，不能一次性同时替换数据库、HTTP、调度器和浏览器而缺少中间质量门禁。
- 每个阶段保持测试可运行，并用窄适配接口隔离 PostgreSQL、Node HTTP 和 Playwright。
- Cloudflare 清理属于最终切换步骤，只能在 NAS 全量验收后执行；它不能作为前期开发步骤。
- 创建任何本地 Git 提交前必须向用户说明精确范围并取得确认；确认后同一操作完成提交与推送，不能只提交不推送。
- 真实 Docker Hub、Telegram、NAS 和 Cloudflare 操作必须使用各自最小权限凭据，且不得将凭据写入仓库、日志、测试或文档。
